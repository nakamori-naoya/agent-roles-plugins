# assign-agent-roles

役割は作業の手順ではなく、産出する成果物の型で分ける。役割ごとの成果物、権限、受け渡し、してはいけないことは、[役割の Catalog](../../roles/catalog.yml) が一か所で持ち、agent fleet に配られた各エージェントもそれを読む。この skill が持つのは、Catalog の役割を仕事へ当てはめるときにエージェントが外しやすい三つの判断である。

## 役割は、その成果物が仕事に要るときだけ立て、兼任で埋めない

全部の役割を毎回立てる必要はない。立てるのは、その役割が産む成果物が仕事に要るときだけである。要る役割の担い手がいないときは、別の役割に暗黙に兼ねさせない。advisor が自分の助言した成果物を review すること、worker が自分の成果物を review することは越境である。担い手がいなければ、足りない役割と、それで未検証になる範囲を報告する。どの役割が要るかが完了条件から一つに決まらないときは、最も筋の良い割り当てを仮説として採り、採らなかった割り当てと、省いたときに未検証になる範囲を添えて確かめる。

エージェントが一体だけの仕事には、役割の割り当てを使わない。そのエージェントは成果物を作る役だけを担い、受け入れと統合は利用者が決める。

## base へ統合できるのは manager だけで、worker は完了報告で止まる

共有の統合先（base branch）へ成果物を統合できるのは、受け入れを決める manager だけである。受け入れる者と統合する者が分かれると、受け入れていない成果物が統合先に入るからである。一者が受け入れと統合の順を持てば、どの成果物をどの順に入れ、残りの作業者にいつ追従させるかも一つに決まる。

統合できる役割であることと、統合してよいことは別の問いである。統合してよいかは利用者が決める。利用者が統合を自分に留めているなら、manager は受け入れと統合の順を提案して止まる。利用者の承認をどう扱い、どう渡すかは git-work-policy に従う。

## reviewer の反証は、受け入れの前に置く

reviewer の指摘の採否は manager が決め、見ていない範囲を「問題なし」に変えない。受け入れは review の後に来る。だから review を、review される成果物の受け入れを前提にした順番に組まない。受け入れた後の review は、受け入れを止められないからである。

## 役割の Catalog は、別の実行の仕組みへ渡すときだけ書き出す

agent fleet のような実行の仕組みへ渡すときだけ、`python3 ../../scripts/export_catalog.py --target "$HOME/.config/agent-roles/catalogs/builtin@2.json"` で検査済みの JSON を書き出して渡す。失敗したら理由を変えずに返す。既に違う内容があると止まるので、差分を確かめて版の扱いを決めてから `--replace` を付ける。Catalog へ書くのは役割の定義と関係だけで、エージェントの実体、model、task、pane のような実行の関心は書き足さない。
