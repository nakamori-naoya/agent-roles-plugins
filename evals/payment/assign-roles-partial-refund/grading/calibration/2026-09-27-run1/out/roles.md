# 部分返金の仕事の役割の割り当て

対象: `job.md`「部分返金を足す仕事」
使えるエージェント: Claude Code ×2（以下 Claude-A / Claude-B）、Codex ×1。同時に動かせるのは三体まで。

## 立てる役割と立てない役割

| 役割 | 立てるか | 理由（完了条件から要る成果物） |
|---|---|---|
| manager | 立てる | 完了条件の判定、reviewer の指摘の採否、受け入れと統合順の提案が要る |
| worker | 立てる | 部分返金の実装と test の結果が要る |
| reviewer | 立てる | 「実装した者とは別の者が」セキュリティ（他店舗の注文を返金できないこと）を確かめる、と完了条件にある |
| researcher | 立てる | 代行会社の部分返金の回数上限と、同じ番号での再送時の振る舞いが未確認で、二重返金の設計がこれで変わる |
| advisor | 立てない | 設計の分岐は「こちらで持つ / 代行会社に任せる」の二択で、researcher の事実が出れば manager が判断できる。三体の枠も足りない（下の「未検証になる範囲」を参照） |

## 割り当て

### manager — Claude-A

- 成果物: 目的・完了条件・停止条件の確定、作業の順序、reviewer の指摘の採否の記録、受け入れの判断と main への統合順の提案。
- 権限: 各役割への依頼と差し戻し。二重返金を防ぐ仕組みをこちらで持つか代行会社に任せるかの決定（researcher の事実にもとづく）。
- 越えてはいけない線:
  - **main へ統合しない**。完了条件に「main への統合は利用者が自分で行う」とあるので、受け入れの判断と統合の手順を提案して止まる。
  - 実装を自分で書かない。review を自分で代行しない。
  - reviewer が見ていない範囲を「問題なし」と書かない。
  - 代行会社への問い合わせ（外部への連絡）はしない。必要なら利用者に依頼する。

### researcher — Claude-B（第1段）

- 成果物: 代行会社の部分返金 API について、次の事実を **出典（URL・文書名）と確認日時** 付きで返す。
  1. 一つの支払に何回まで部分返金を受け付けるか
  2. 同じ返金の番号（idempotency key 等）で二度送ったときの振る舞い
  3. 部分返金の合計が支払額を超える要求への振る舞い
- 権限: 公開の開発者向け資料を読む。repository は読むだけ。
- 越えてはいけない線:
  - どちらの設計にすべきかの推奨をしない（事実と、資料で確かめられなかった点だけを返す）。
  - 代行会社へ問い合わせない。公開資料で決まらない点は「未確認」として manager に返し、問い合わせは manager 経由で利用者に依頼する。
  - コードを書かない。

### worker — Codex

- 成果物: 自分の作業 branch 上の部分返金 API の実装と test、および test の実行結果（既存の全額返金 test を含む全件）。
  - 返金の合計が支払額を超えないこと
  - 同じ返金の要求が二度届いても二重に返金しないこと（方式は manager の決定に従う）
  - 代行会社の部分返金 API を呼ぶこと
  - 他店舗の注文を返金できないこと（認可の確認）
- 権限: 割り当てられた作業場所と作業 branch の読み書き。片付けてよいのもそれだけ。
- 越えてはいけない線:
  - 完了報告で止まる。**main へも共有の branch へも統合しない**。
  - 自分の成果物を「review 済み」「安全」と評価しない。
  - 二重返金の方式を自分で決めない。researcher の事実が出る前は、合計額の上限と店舗の認可の部分から着手する。

### reviewer — Claude-B（第2段、新しい session で起動）

- 成果物: 作業の経緯から独立した、再現できる反証。特に
  - 他店舗の注文 ID・支払 ID で部分返金を要求したときに拒否されるか
  - 同じ要求の同時・連続の再送で二重返金が起きないか
  - 合計額の上限を境界値や並行要求で超えられないか
  を、再現手順（test かリクエスト）つきで返す。見た範囲と見ていない範囲を明記する。
- 権限: worker の branch を読み、手元で test を書いて走らせる。
- 越えてはいけない線:
  - 直さない（修正は worker に戻す）。指摘の採否は決めない。
  - worker の説明や途中経過を前提にしない。
- 起動の条件: researcher の仕事が終わって Claude-B の枠が空いてから、**researcher の文脈を持ち越さない新しい session** で起動する。実装者（Codex）とは別の者なので、完了条件の「実装した者とは別の者」を満たす。

## 順序

1. 同時に起動: manager（Claude-A）、researcher（Claude-B）、worker（Codex）。worker は合計額の上限と店舗の認可から着手。
2. researcher が事実を返す → manager が二重返金の方式を決め、worker に渡す。公開資料で決まらなければ、manager が利用者に代行会社への問い合わせを依頼し、答えが来るまで方式の決定を止める。
3. worker が完了報告（実装と全 test の結果）で止まる。
4. reviewer（Claude-B の新しい session）が反証を返す。**受け入れはこの後**。
5. manager が指摘の採否を決め、必要なら worker に差し戻して 3–4 を繰り返す。
6. manager が完了条件を一つずつ照らして受け入れを判断し、main への統合の手順を利用者に提案して止まる。統合は利用者が行う。

## 未検証になる範囲・仮説

- **advisor を立てていない**ので、二重返金の方式（自前で持つ / 代行会社に任せる / 両方）のトレードオフは manager 以外に独立に検討されない。manager の判断が単独になる。これが気になる場合、第1段で Claude-B を researcher ではなく advisor にする案もあるが、その場合は事実の調査を担う者がいなくなるので採らなかった。
- **代行会社への問い合わせ**はエージェントが行えない（外部への連絡）。公開資料で決まらない点は利用者の問い合わせ待ちになる。
- reviewer の範囲は完了条件に明記されたセキュリティ（他店舗の注文）と二重返金・上限額に絞っている。それ以外（ログへの個人情報の出力、監査記録など）は review されない。
- Claude-B が researcher と reviewer を段を分けて担うのは、三体の枠に収めるための仮説。researcher は実装にも設計の推奨にも関わらないので独立性は保たれると判断したが、manager を利用者自身が担うなら、Claude-A を reviewer に回して Claude-B を researcher 専任にする割り当ての方が単純になる。
